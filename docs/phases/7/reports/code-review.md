## Findings

**1. BLOCKING -- MT-003 step 6 fails on a correct product.** `test/manual/MT-003-long-command-through-the-edge.md` step 6 reads 100 bytes from step 4's `next_offset` and expects `.eof == true`. `eof` is true only when the page reaches the end of the output (`internal/jobs/read.go:123`; `tool_commands.go` `EOF: out.EOF && t.used == len(out.Data)`). The command prints a line every second and runs through steps 3 to 5, so more than 100 bytes usually lie past that offset. The result is `eof: false` and the test reports FAIL. That blocks the release. `wait_seconds` also does nothing here, because output past the offset already exists. The header's "step 6 waits inside one call" is therefore false. Fix: `read_output {"command_id": "<command-id>", "offset": -1, "max_bytes": 100, "wait_seconds": 10}` with the same Expect. Also remove the reuse of `<next-offset>` and the "waits inside one call" wording.

**2. ADVISORY -- the unit's config failures do not produce `config problem` lines.** `docs/operator-guide.md:158` says a bad config "shows in `journalctl -u yasshm` as one `config problem` line per problem". The unit runs `ExecStartPre` = `config check`, and `runConfigCheck` prints the plain `path: message (line N)` lines to stderr (`internal/cli/cli.go`). `serve` never starts, so no JSON `config problem` line is written. Should read: "...shows in `journalctl -u yasshm` as the `config check` lines, `path.to.key: message (line N)`, one per problem (when `serve` is run by hand, as `config problem` JSON lines)."

**3. ADVISORY -- `passwd --lock` conflicts with the troubleshooting advice.** `deploy/README.md:68` locks the `look` account. `operator-guide.md:275` (`ssh_auth_failed`) tells the operator to check "that the account is not locked". On a target with `UsePAM no`, `sshd` refuses public-key login for a password starting with `!`. Fix: replace step 4's `passwd --lock look` with `usermod -p '*' look` ("no password login, not locked"). Add to the `ssh_auth_failed` row: "on a target with `UsePAM no`, a password field starting with `!` refuses key login".

**4. ADVISORY -- the ssh-keyscan line is not a `host_key` line.** `deploy/README.md:97-101`: `ssh-keyscan` writes `host type base64`, but `host_key` takes the `authorized_keys` form. Pasting the scanned line fails `config check`. This fails closed, but the step reads as if the paste works. Add: "drop the host name `ssh-keyscan` puts first, or name the scanned file (after the fingerprint matches) in `known_hosts_file`".

**5. ADVISORY -- the per-server limit is two counts.** `operator-guide.md:87` and `:256`, and the example's comment at `config.example.yaml:146`, say `max_concurrent_per_server` bounds "commands, probes and transfers" together. `takeTransfer` (`internal/mcpserver/gateway.go:578`) counts probes and transfers "apart from commands", so one server can hold twice the limit in SSH connections. Should read: "Commands running at once on one server, and separately probes and file transfers running at once on one server."

**6. ADVISORY -- the version string a release carries.** `README.md:83` says "the tag for a release". `release.yml` builds with `VERSION="${TAG#v}"`, so `yasshm version`, `gateway.started` and the file names carry `0.1.0`, not `v0.1.0`. The same line says "the short commit" for a `mise run build`. That holds only with no tag reachable: `scripts/build.sh` uses `git describe --tags --always --dirty`. Should read: "the version without its `v` for a release (`0.1.0`, file `yasshm_0.1.0_linux_amd64`), and `git describe --tags --always --dirty` for a local `mise run build`". Also state the no-`v` file name in `deploy/README.md:40`.

**7. ADVISORY -- missing operational fact: the seven-day key age.** `internal/auth/keyset.go:34` (`MaxKeyAge`) drops the last good key set seven days after the last successful fetch. After that, every request is `keys_unavailable` (503) and `/healthz` reads `degraded`. The guide (`:305`) says only "keeps the last good keys". Add: "A failed fetch keeps the last good keys for at most seven days after the last successful fetch; after that every request is refused with 503 until a fetch succeeds."

**8. ADVISORY -- the manual tests assume the runner sees structured content.** MT-001 to MT-004 write "the result's structured content verbatim". The text blocks are a human-readable header plus raw output (`call.go:341`, `pageHead`), not JSON. A Claude Code runner that is shown only `content` cannot produce the file. Every `jq` step would then be BLOCKED. State this in each Runner bullet as a precondition (the client exposes `structuredContent`), with the BLOCKED classification. Or confirm it first in MT-001.

**9. ADVISORY -- the unit's first start: name where it will bite.** Most likely failures, in order: a `ReadWritePaths` directory missing (226/NAMESPACE; covered at `operator-guide.md:325`); DNS or egress to the key-set host; and a system call `@system-service` minus `@privileged @resources` denies. With `SystemCallErrorNumber=EPERM`, that last one appears as an "operation not permitted" error, not a crash. `MemoryDenyWriteExecute`, `PrivateDevices`, `ProtectProc=invisible`/`ProcSubset=pid`, no `AF_NETLINK` and `flock` are all fine for a pure-Go binary with modernc SQLite and the pure-Go resolver. Add one row to "The gateway will not start": "an `operation not permitted` error after `listening` or during a fetch: comment out the two `SystemCallFilter` lines to confirm, and report it."

**10. ADVISORY -- doc tests that check against a copy.** `internal/store/guide_test.go` hand-lists the seven statuses, so a new status passes unnoticed. Derive the list from `store`'s transition table (`records.go:42`, keys plus values). `internal/config/example_test.go` `TestUnitStopTimeout` hard-codes the 5 seconds that `cli.httpCloseWait` holds. Export it, or move the test into `internal/cli`. In `scripts/check.sh` `run_deploy`, the second `go test -run '^(TestWorkflow|TestExample|TestUnitStopTimeout)'` has no `-v` and no PASS count, so a renamed test passes it vacuously (the `test` step still runs them). `trap ... RETURN` does not fire on `exit 1`, so temp files leak on failure. `ours` is not `local`.

**11. ADVISORY -- the quick start races and reaches the network.** `README.md:76-77` runs `curl` straight after starting `serve &`, before the port is bound. `curl -s` then prints nothing. Insert `sleep 1`. The example's team domain makes a real HTTPS request to a `cloudflareaccess.com` name that a stranger could register, and then `/healthz` would read `ok`. Say "usually `degraded`", or add a `certs_url` that points at an unused loopback port to the quick-start `sed`. `/tmp/yasshm-try` is a predictable shared path; `T=$(mktemp -d)` is better.

**12. ADVISORY -- operator prerequisites not written down.** `SECURITY.md:5` relies on GitHub private vulnerability reporting, which is off by default. Add "enable private vulnerability reporting" to the attended queue in `GOAL.md` before the tag. In `release.yml`, a rerun after a partial `gh release create` failure fails on the existing release. A line in `deploy/README.md` or the changelog process should say to delete the draft or release first.

Nothing is interpolated in `run:`. `contents: write` is set only in `release`. `--verify-tag`, `--prerelease` on a hyphenated tag. Concurrency is queued. An existing release fails closed.
- Install order: user and directories, then key as `yasshm`, then config `0640 root:yasshm`, then `config check` as the service user, then the unit. These match `keyfile` (euid owner, no group or other bits), `config` (no group or other write), `store.CheckPrivateDir` and `audit.Open` (directory without group or other write; file 0600 owned by euid).
- The `authorized_keys` line (`restrict`, no `command=`). Host key pinning without trust on first use. Checksum names match `scripts/build.sh`. Upgrade, rollback with forward-only schema (`ErrTooNew`), uninstall.
- `TestManualTests` enforces the header bullets, the `(live k)` numbering and the budget equality. The MT-001, 002, 004 and 005 Expects are decidable against the actual field names.
