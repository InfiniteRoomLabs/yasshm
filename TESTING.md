# TESTING.md -- how yasshm tests

Referenced from `CLAUDE.md` and `README.md`. This is the single source of truth for **how we test**; the concrete steps are the ones `scripts/check.sh` runs. The gate, in order, is `fmt` (gofmt reports nothing), `lint` (golangci-lint, `.golangci.yml`, warnings are errors, `nolint` needs a named linter and a reason), `skipcheck` (no skipped test without an issue link on the same line), `test` (`go test -race -shuffle=on -count=1` with a coverage profile over all packages, written to the gitignored `coverage.out`), `sshd` (the real-`sshd` half of the SSH contract suite; see below), `e2e` (the end-to-end suite against the real binary; see *The end-to-end layer*), `deploy` (the unit, the example config and the workflows; see *Deployment files and docs*), `docs` (Markdown links, ASCII, placeholders and wrapping), `cover` (total at or above the floor, 85 percent, `internal/testkit/...` the only exclusion; it fails if there is no profile, so run `test` first), `vuln` (`govulncheck ./...`), `build` (the release files in `dist/`) and `arch`. Each runs alone as `mise run check -- <step>`. A dirty tree fails the gate. The SSH contract suite (`internal/sshclient`, one table of scenarios) runs against two servers: the in-process `internal/testkit/sshtest` everywhere, and a real OpenSSH `sshd` started by `internal/testkit/realsshd` as the current user on a random loopback port, which only CI has (spec section 7). The real-`sshd` tests are named `TestRealSSHD*` and are ordinary tests with no build tag: without `sshd` they log one line and return (never `t.Skip`), and with `YASSHM_REQUIRE_SSHD=1` (set by CI) they fail instead. The `sshd` step runs them verbosely with `YASSHM_REQUIRE_SSHD=1` when `sshd` is present, together with the in-process half, and fails unless the number of `TestRealSSHDContract/` scenarios that passed equals the number of `TestContractSSHTest/` scenarios that passed in the same run, and the real-`sshd` login test passed; it prints `sshd`'s version and the `F10 observed` and `A8 observed` lines, which are the evidence the QA lane reads in the CI job log. After each scenario both halves assert that no process the server's sessions started is left (real `sshd` tags its sessions with an environment marker), and every test that could hang has a bounded wait. Without `sshd` the step prints one line saying the real-sshd lane runs in CI only, and with `YASSHM_REQUIRE_SSHD=1` it fails. Coverage of `internal/sshclient` comes from the in-process half alone, so the local gate measures it. SSH tests use short timings (fractions of a second for the kill grace and connect timeout), end with the connection closed and check that no goroutine of the client or the test server outlived them. A `cover` result counts only right after `test` on the same tree (the full gate always does that). Test helpers that can skip live only in `_test.go` files or `internal/testkit/`. `mise run fuzz` runs every `Fuzz*` target for 30 seconds each and is not part of the gate; the targets' seed corpora (`f.Add` and `testdata/fuzz/`) run in the gate as ordinary tests. The dependency rule of spec section 4 is a test (`internal/deprule`), not a lint rule: it parses the imports of each package it knows and fails on one the rule does not allow; add a package to its table when its phase builds it. It also walks `cmd/`, `internal/` and `test/` and fails when a file other than a `_test.go` file imports `internal/testkit`. Synthetic config files for tests come from `internal/testkit/configtest`. The job engine's tests (`internal/jobs`) build two tenants in code on in-process SSH servers, drive every status through the real engine with the server's fault switches, run in parallel and check connections and files open under the data directory; the goroutine leak check sees the whole process, so it runs only in `TestLeaks`, which is not parallel; the janitor runs with an injected clock and `Sweep`, never by sleeping for its interval. The authenticator's tests (`internal/auth`) run against `internal/testkit/accesstest`, a local issuer on a loopback port that serves the key set, counts fetches, rotates keys, goes down and misbehaves on a switch, and mints every token class by hand (the hostile ones included); the clock is injected, so the once-a-minute refetch limit and the 30-second leeways are tested by moving it, never by sleeping, and one test scans everything captured (audit log, logs, errors, bodies) for the token, its segments and the key material. The deadline-bounded poll, the goroutine leak check and the 0700 temp directory these tests and the SSH tests share are `internal/testkit/leakcheck`; store failures (a full disk) are injected through the engine's `hooks`, because a test cannot mount a small file system as a normal user. The sandbox runs as root, so a test that needs an unwritable file uses something that fails for root too (`/dev/full` for a failing write, a path under a regular file or a directory for a failing open), and key permissions are checked on the mode bits. The MCP endpoint's tests (`internal/mcpserver`) go through the real HTTP handler on a loopback port with the SDK's own client (`mcp.NewClient` with `StreamableClientTransport`), real `sshtest` targets, a real audit log, the real job engine on SQLite and the local issuer, with two tenants built in code; raw JSON-RPC posts measure response bodies, and `internal/testkit/edgetest` stands in for the edge. The audit log is wrapped so a named event fails (`internal/testkit/audittest`, shared with the job engine tests, as are the limits, SSH options and servers of `internal/testkit/tenanttest` and the log sink `internal/testkit/syncbuf`), which is how audit-before-act is tested event by event; a really broken log refuses `auth.accepted`, so the guard answers 503 before any tool. The D8 marker test gives the hosts, users, key and `known_hosts` paths and identity ids of the config unique strings (unreachable "ghost" servers fail on their missing key before any dial, so no name is ever resolved) and scans every result, error, schema, header and log line for them. `serve` (`internal/cli`) is tested in-process with `cli.Serve` and a cancelled context, and once as a child process stopped with `SIGTERM` (`cmd/yasshm`); a test that builds a config for it points `certs_url` at the local issuer or at `loopback.RefusingPort`, never at a real team domain. How the rules below apply to this project (the layers, the test support packages, the scenarios) is spec section 7 (`docs/superpowers/specs/2026-11-18-yasshm-design.md`).

## The end-to-end layer

`test/e2e` (package `e2e`, tests only) builds the real binary once per run with the flags of `scripts/build.sh` (CGO off, `-trimpath`, the `-X` version variables with test values) by the `go` on `PATH`, which must be the toolchain the suite was built with (so run it through `mise`), and starts `yasshm serve` as a child process per scenario: port 0, its own private data directory, audit log, config and keys, the local issuer (`accesstest`), `sshtest` targets and the stand-in edge (`edgetest`). The bound address comes from the binary's `listening` log line; every wait is bounded and waits for an event (a log line, a `/healthz` status, an output marker, a tool's status, an audit event). Every child runs in its own process group, is stopped with `SIGTERM` at cleanup (a child that does not exit within 30 seconds fails the test and is killed with its group), and its stderr is attached to the log of a failed test, and its stderr and audit log are scanned for token and private key text; after each scenario no command the targets started may be left. The `scenarios` table in `test/e2e/scenarios_test.go` maps each spec section 7 scenario to its test, and `TestScenarioTable` holds the table, the package and the spec 7 callout to each other. The suite may import only the test kits and, to read what the gateway wrote, `internal/audit` and `internal/store` (`internal/deprule` enforces it; today it parses the audit log itself and imports neither): every answer it checks comes from the binary. The scenarios are spec section 7's list; each is a top-level `TestE2E<scenario>` whose subtests carry the path class. Two tenants cannot run against the binary (the loader accepts one, D7), so isolation stays in-process (`internal/mcpserver` and `internal/jobs`) and the suite proves that two tenants are refused. The audit log is made unwritable under a running gateway by lowering its `RLIMIT_FSIZE` with `prlimit(2)` (no privilege needed, binds root too, the Go runtime ignores `SIGXFSZ`, so the write fails with `EFBIG`). `TestE2EResourceBounds` sends a burst of 200 mixed calls and checks that the gateway's `/proc/<pid>/fd` count returns to its idle value and its RSS stays under a ceiling.

The gate runs the suite in its own step, `e2e`, after `sshd`: the test process under `-race`, the binary a normal build, verbosely; it counts the top-level `TestE2E*` functions with `go test -list` and fails unless as many report PASS and `TestScenarioTable` passes. The `test` step leaves `./test/e2e` out, so the suite runs once and adds nothing to the coverage total (the package has no statements). Run it alone with `mise run check -- e2e`, or one scenario with `CGO_ENABLED=1 mise exec -- go test -race -count=1 -v -run 'TestE2ELongCommand' ./test/e2e` (a subtest class with `-run 'TestE2E.*/sad/'`).

## What gets an automated test, and what cannot

Everything that can run without the real edge, a real target host or a secret gets an automated test in the gate: unit, integration and end to end. No test reaches the network, a real host or a credential. What cannot be automated under those limits is a manual test (last section), run by the operator and never by the build loop.

## The green rule -- always run green, never ignore, never silence

Non-negotiable, enforced by tooling, not honor system:

- **Never skip or focus:** no `.skip`, `.only`, `.todo`, `xit`, `t.Skip`, `@pytest.mark.skip` or their equivalents in committed tests without an inline link to a tracked issue. Ban them in the linter **and** in a `check.sh` grep step, not in a review checklist.
- **Never silence:** no blanket ignore pragmas (`@ts-ignore`, `eslint-disable`, `# noqa`, `//nolint`, muted output) without an inline justification linked to an issue.
- **Never ignore:** a failing test blocks the merge. There is no "known-failing" allowance -- intentionally divergent behavior is fixed or locked in by a *passing* test that documents it.
- **Warnings are errors.** Lint and compiler warnings fail the gate.

`mise run check` must be green on a clean tree (`git status --porcelain` empty) before any phase merges. A dirty tree fails the gate, because a green result on a dirty tree describes disk, not HEAD.

## The pyramid

Bias toward the cheapest layer that can catch the bug: unit and functional tests at the base, integration above, end-to-end at the tip. A bug found by an e2e test that a unit test could have caught is a missing unit test.

## Path taxonomy

Tag test names so triage can grep them. A feature is not done until every applicable tag is covered. In Go the tag is the first element of the subtest name (`t.Run("sad/unknown key", ...)`), so `go test -run '/sad/'` selects a class.

| Tag | Covers |
|---|---|
| `happy` | the intended path with valid input |
| `sad` | invalid input, expected failures, error responses |
| `raging` | hostile or malformed input, abuse, limits exceeded |
| `edge` | boundaries: empty, one, maximum, unicode, time zones |
| `corner` | two or more edges at once |

## Coverage

Set a floor and enforce it in the gate (`scripts/check.sh`), not in promises. Excluding files from the measurement is a design decision: flag it in the same commit and keep the excluded set tiny (an entrypoint with one statement, not "everything hard to test"). For yasshm the floor is 85% of statements across all packages, and the only exclusion is the test support code in `internal/testkit/` (spec section 7).

## Deployment files and docs

The files an operator installs and reads are tested like code, so they cannot drift from it. The `deploy` step runs `./deploy` (every directive of the systemd unit of spec section 8 is present with its value; no `Environment=` and so no `MCPGODEBUG`; no active `IPAddressDeny`; the example config runs through `yasshm config check` once a generated key and host key replace its two placeholders, and is refused as shipped), the example-config tests in `internal/config` (every limit's default and range in the comments equal the limits table, every key the decoder accepts is in the example, `TimeoutStopSec` exceeds the largest graceful stop), `TestWorkflow*` in `internal/deprule` (release trigger, SHA pins, permissions, no interpolation in `run:`) and `systemd-analyze verify` on a copy of the unit with a stub binary path, where the tool exists (any line it prints about the unit fails the step). The `docs` step runs `TestDocs*` in `internal/deprule`: every relative Markdown link and anchor resolves (the lane reports under `docs/phases/` are point-in-time records and are exempt from the link and the wrapping checks), every `.md`, `.yaml`, `.yml`, `.service`, `.sh` and `.toml` file is ASCII, the template-placeholder grep is empty and no prose paragraph is hard-wrapped. The operator guide's tables and sample audit lines are compared with the code by tests in `internal/config`, `internal/mcpserver`, `internal/store`, `internal/audit` and `internal/cli`; `SECURITY.md`'s tables are compared with spec section 6 (`TestSecurityMDMatchesSpec`); the manual tests' format is checked by `TestManualTests`.

## Manual tests

Live checks the suite must never run are manual tests in `test/manual/`, one `MT-<nnn>-<name>.md` beside its `.results` log, in the agent-ops `manual-test` format: one tool call per step, a `jq -e` or exact-shape expected result, a declared read budget, placeholders resolved from the gitignored `mise.local.toml`. They run at release (release-prep Step 4a) and a FAIL refuses the tag. Each names what blocks its automation; the count of active files is tracked debt. Active: MT-001 to MT-005 (spec section 7), written in Phase 7 and not yet run: MT-001 a Claude connector signs in through the real edge, MT-002 the look account is unprivileged and a denylisted command is refused, MT-003 a long command survives the edge, is paged and killed, MT-004 a crashed gateway reads a running command as lost, MT-005 the public hostname refuses an unsigned request. Each is blocked on the same thing -- it needs the real edge and a real target, which the build loop never has -- and names when it could be automated.
